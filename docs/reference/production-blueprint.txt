Pharmacy ERP & POS — Production Development Blueprint
Commercial SaaS specification
Product: Multi-Tenant Pharmacy Management, ERP & Point-of-Sale Platform
Market: Bangladesh first, internationally extensible
Platforms: Cloud web application + desktop POS with controlled offline operation
Architecture: Secure modular monolith with independently deployable worker services
Primary users: Pharmacy owners, pharmacists, cashiers, inventory managers, accountants, wholesalers, and platform administrators
This blueprint is designed for building a genuine commercial software product—not a dashboard demonstration or basic CRUD application.
The finished platform should support medicine purchasing, batch-level inventory, prescription workflows, retail and wholesale sales, financial accounting, branch operations, regulatory controls, and centralized SaaS administration.
It should also support real pharmacy hardware, including barcode scanners, receipt printers, cash drawers, and label printers.
1. Product principles
The entire development process should follow six requirements:
1. Correctness before features: Sales, inventory, payments, and accounting must remain consistent under concurrent usage, network failures, and application crashes.
2. Security by design: Authorization, tenant isolation, encryption, auditability, and secure deployment are fundamental architectural requirements.
3. Pharmacy-specific workflows: Medicine batches, expiry, recalls, prescriptions, and regulated product restrictions cannot be treated like ordinary retail inventory.
4. Practical offline operation: A disconnected POS must not create unresolvable duplicate sales, oversell shared inventory, or bypass pharmacist approval.
5. Professional UX: Interfaces should prioritize rapid transactions, clear warnings, efficient navigation, and minimal repetitive data entry.
6. Commercial maintainability: The codebase must be understandable, testable, observable, documented, and deployable without depending on the original developer.
Important: No architecture can guarantee a system cannot be hacked. The release criteria must instead require independently verified security controls, tested recovery procedures, and documented residual risks. Bangladesh-specific legal, tax, prescription, and licensing requirements must be validated with qualified local professionals and relevant authorities before production launch.

5. Database architecture and core schema
For a commercial SaaS product, the database design is one of the most important decisions.
I recommend shared PostgreSQL infrastructure with strict tenant isolation, using tenant-scoped composite foreign keys and PostgreSQL Row-Level Security as defense in depth. The application must still enforce authorization itself.
Core entity relationships

The diagram is intentionally simplified. The actual schema needs separate sale lines, purchase lines, stock locations, prescription records, journal entries, reservations, and many-to-many relationship tables.

Example: batch-level inventory model
CREATE TABLE stock_batches (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    branch_id UUID NOT NULL,
    product_id UUID NOT NULL,
    batch_number VARCHAR(100) NOT NULL,
    expiry_date DATE NOT NULL,
    unit_cost NUMERIC(18, 4) NOT NULL
        CHECK (unit_cost >= 0),
    status VARCHAR(30) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL
        DEFAULT NOW(),

    UNIQUE (tenant_id, id)
);


This is illustrative, not the complete migration. Production tables must include appropriate composite foreign keys, indexes, validated status constraints, and additional business attributes.
For the inventory engine:
- stock_movements records every movement with a signed quantity, reason, source document, and actor.
- stock_balances provides concurrency-controlled current quantities.
- stock_reservations prevents checkout and offline allocations from competing for the same units.
- stock_batches maintains product batch identity and expiry information.
- A reconciliation process verifies that materialized balances match ledger movements.
Important database invariant: Available quantity must never become negative. Posted financial transactions must balance, and completed operations must never be processed twice because of repeated API calls.

10. Bangladesh-specific production considerations
Before accepting live pharmacy customers, establish a compliance register covering:
- DGDA: Pharmacy licensing, medicine classifications, dispensing and recordkeeping requirements applicable to the intended businesses.
- NBR: Applicable VAT, invoicing, fiscal recordkeeping, and tax treatment.
- Payments: Merchant onboarding, transaction confirmation, refunds, settlement, and reconciliation for supported payment providers.
- Patient information: Access controls, privacy notices, lawful processing, retention, and breach-response obligations.
- Pharmacy hardware: Actual supported printer models, barcode scanners, and Windows/Linux driver behavior.
These requirements must be checked against current authoritative guidance. They should not be inferred from competitor advertisements.
11. Recommended first implementation
I recommend starting with a vertical slice that can be thoroughly tested:
Tenant registration → branch creation → medicine catalog → batch receiving → barcode checkout → receipt → stock ledger → sales report.
This gives you a working end-to-end pharmacy operation and a strong foundation for every later module.
Use a private repository during development, configure branch protection and mandatory CI checks, and keep separate development, staging, and production environments.
Do not populate production with fictional patient data, use real customer credentials for testing, or publicly expose development databases.
Final project deliverables
The complete product should ultimately include the source code, versioned database migrations, OpenAPI specification, architecture decision records, automated test suites, desktop installers, deployment configuration, operational runbooks, security documentation, backup/restore procedures, administrator documentation, and role-specific user manuals.
