4. Security requirements
No software can be guaranteed impossible to hack. A professional product should instead be designed to reduce attack risk, limit damage, detect incidents, and recover safely.
I would require:
- Server-side permission checks on every sensitive operation, MFA for privileged users, secure session management, and account lockout/rate limiting.
- Strict tenant and branch isolation, including authorization tests that attempt cross-tenant access.
- TLS, encrypted backups, secrets management, secure cookies, CSRF protection, and protection against XSS, SQL injection, and insecure file uploads.
- Immutable-style append-only audit records, with restricted access and tamper detection.
- Database transactions and concurrency controls to prevent double sales, duplicate payments, and incorrect stock deductions.
- Dependency scanning, static analysis, penetration testing, backup restoration drills, and incident-response procedures.
- Controlled medicine workflows, prescription verification, and approval requirements configured to applicable local law.
For Bangladesh, the implementation should also be reviewed against applicable DGDA requirements, medicine-sale restrictions, tax/VAT rules, and privacy obligations before commercial deployment.
5. A critical technical decision
Inventory must not be stored as a single editable quantity field without a transaction history.
Use a stock movement ledger recording purchases, sales, returns, transfers, adjustments, damage, and expiries. Maintain batch-level quantities and derive or reconcile available stock from those movements.
For example, if two cashiers sell the last medicine simultaneously, the database must prevent both transactions from succeeding against the same available unit. This requires transactional locking or equivalent concurrency-safe stock reservation logic.
This is the kind of detail that separates a polished demonstration from a reliable commercial system.
6. Development roadmap
Phase	Deliverables
1. Foundation	Requirements, database design, design system, authentication, roles
2. Core pharmacy	Medicine catalog, suppliers, batch inventory, stock ledger
3. POS	Billing, barcode, receipts, payments, returns
4. Procurement	Purchase orders, goods receiving, reordering
5. Finance	Expenses, profit calculations, cash reconciliation
6. Operations	Prescriptions, expiry, rack management, alerts
7. Enterprise	Multi-branch, analytics, centralized controls
8. Hardening	Security tests, load tests, backups, disaster recovery
9. Launch	Pilot pharmacy, staff training, monitored rollout
Every phase should have automated tests and explicit acceptance criteria. Do not postpone security and data-integrity testing until the end.
7. Making it a professional developer project
Your repository should contain purposeful code, readable module boundaries, meaningful commits, normal technical documentation, tests, and deployment instructions.
Avoid artificial milestone diaries, generic filler comments, unnecessary abstractions, or copied UI. Code comments should explain business rules and non-obvious technical decisions, not narrate the development process.
You can use coding assistants during development, but no prompt can establish that software was entirely hand-written. What matters is that you understand, review, test, and take responsibility for the implementation.
